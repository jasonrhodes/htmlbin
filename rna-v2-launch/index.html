A new way to think about
alerting in Elastic

A ground-up redesign of alerting in Elastic. One query language for all alert logic. Full alert history you can search. Smarter noise control. And rules that can watch other rules.

v1 is not going away. v2 runs alongside your existing rules and alerts. Enabling it changes nothing about v1. There is no forced migration — teams move rules at their own pace, when they’re ready.
Why we built this

Real problems we've heard from you

If any of these feel familiar, you're not alone. Every one of these drove a design decision in the new alerting experience.

Today

"I need a new detection, but there's no rule type for it"

Every alerting use case requires a hand-built rule type shipped by Elastic. New detection logic means waiting for a release.

With v2

Any ES|QL query is a rule

Write your detection as an ES|QL query. No executor plugins, no waiting for Elastic to ship a new rule type. If you can query it, you can alert on it.

Today

"The alert fired, but I can't see what value triggered it"

What gets stored in an alert is decided by the rule type's executor, not by you. Getting one more field means asking Elastic to change the rule type code.

With v2

You control the payload

Your ES|QL query is the alert payload. Whatever fields you select end up in the event — and they accumulate as a time series across the life of the episode, not a single snapshot.

Today

"It keeps flapping and I can't make it stop"

No custom recovery logic. The system decides when an alert is "recovered." Noisy signals become noisy pages with no way to add hysteresis.

With v2

Custom recovery, delayed activation

Define a separate recovery query with a different threshold than firing. Require N consecutive breaches before activation. You decide when something is truly a problem — and when it's truly fixed.

Today

"Three alerts fired for the same incident, but the system doesn't know that"

Alerts can't see other alerts. Correlating multiple signals into one incident happens in your head or in an external tool. The system has no way to say "these are the same incident."

With v2

Rules on rules

Alert output lands in a searchable data stream. Write a second rule that queries it — "fire when 3+ hosts breach memory thresholds simultaneously." One incident, not three pages.

Every rule evaluation is retained and searchable.
Ask "why did I get paged?" or "why didn't I get paged?" — and get a real answer.

What's new

Built from first principles

A new engine with new primitives — running alongside v1, not replacing it.

☰

ES|QL-native rules

One language for all alert logic. Thresholds, absence checks, aggregations, correlations — all expressible in ES|QL. Three authoring modes: visual builder, ES|QL editor, or AI-assisted.

⏱

Episode lifecycle

Alerts have a real state machine: Pending → Active → Recovering → Inactive. Configurable thresholds at each transition. Signal vs. Alert mode for different use cases.

📨

Action policies

Notification routing decoupled from rules. One policy can serve many rules. Match, group, and throttle independently. Four throttle strategies. No more per-rule action configuration.

🔍

Full audit trail

Every evaluation writes to .rule-events. Every dispatch decision writes to .alert-actions. Query both in Discover. "Why did this fire?" has an answer.

🔗

Rules on rules

Rule events are just data. Write a meta-rule that queries them — blast radius detection, escalation chains, cross-service correlation — all in ES|QL.

🤖

AI-assisted authoring

Describe what you want to detect in plain language. The agent builds the ES|QL query, configures thresholds, and wires up the action policy. Edit and refine from there.

At a glance

v1 vs v2

Capability Alerting v1 Alerting v2
Rule logic Fixed rule types with hard-coded executors Any ES|QL query
Alert data Executor decides what's stored You choose via KEEP — full time series per episode
History Updated in place — latest value only Append-only — full evaluation history
Recovery System-defined, no custom logic Custom recovery query + delayed activation
Notifications Per-action on each rule Action policies: match, group, throttle across rules
Rules on rules Not possible Alert output is queryable data — meta-rules, escalation chains
Audit trail Limited — hard to answer "why did this fire?" Full — query .rule-events and .alert-actions in Discover
External alerts Manual via connectors (outbound only) Push API — ingest from any source, same lifecycle
