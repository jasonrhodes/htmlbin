UNKNOWN_D
Limbo: group present in has_data query but meets neither the breach nor recovery threshold
Write rule_event.status: 'breach'. Episode status unchanged.
The value didn't meet the recovery condition — the only options are to reuse an existing status or invent a new one. Reusing breach is honest: the episode is still active and nothing has changed. Inventing a new status requires threading it through the state machine and all downstream consumers.
UNKNOWN_E
No recovery configured: group stopped breaching but is still present (or ambiguously absent with no_data_strategy: none)
Write no event. Episode drifts out of lookback windows over time.
Users who set recovery_strategy: none explicitly opted out of automatic recovery. The episode stays notionally active but will fall outside most query lookback windows. This is an acceptable trade-off — it's the user's choice, and adding a silent auto-recovery would violate their intent. Additionally, writing breach events in perpetuity to keep the episode alive would not be scalable.
